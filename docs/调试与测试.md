部署只有一种（单容器 + 两个端口），见
[单容器部署（all-in-one）](<单容器部署（all-in-one）.md>)。本文讲**怎么测**和**怎么查**。

## 1. 测试

### 1.1 测试矩阵

| 层 | 命令 | 规模 | 需要什么 |
|---|---|---|---|
| Rust 引擎 | `cargo test -p dogwood-local-engine` | 全绿 | 无 |
| Rust HTTP 适配器 | `cargo test -p dogwood-http` | 34（12 单元 + 5 DTO 漂移 + 17 端到端） | 无（端到端用假引擎，绕开平台限制） |
| Rust 全工作区 | `cargo build --workspace --all-targets` | CI 的门槛 | 无 |
| Python SDK 协议层 | `PYTHONPATH=python-sdk python3 -m unittest discover -s python-sdk/tests -p 'test_framing.py'` | 10 | 无 |
| Python SDK 本地引擎 | 同上，`-p 'test_live.py'` | 6 | 同机的 `dogwood-server` |
| Python SDK HTTP | 同上，`-p 'test_http_transport.py'` | 18（5 条要适配器） | 部署在跑 |
| 端到端自检 | `./dogwood-http/examples/smoke.sh` | 10 条断言 | 部署在跑 |
| 用例集（写规则 + 验裁决） | `python3 dogwood-http/examples/testcases.py --all` | 自定义 | 部署在跑 |

**macOS 上的已知红灯：** `cargo test --workspace` 会有 23 个控制面测试失败——那不是回归，
是控制面依赖 Linux 的 `SO_PEERCRED`（见 §3.3）。要跑它们就进容器。

### 1.2 两个"退出码就是结果"的自检

```bash
# 引擎容器活着吗（探针会去 ping 引擎，所以 200 = 引擎也在答）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/healthz

# 全链路：装策略 → 403 → 记录批准 → 200
./dogwood-http/examples/smoke.sh
```

### 1.3 SDK 的测试怎么跑

SDK 的 endpoint 决定传输，所以同一套测试有两种跑法：

```bash
# ① 对 HTTP（在宿主机上跑，不需要 socket）
PYTHONPATH=python-sdk \
DOGWOOD_ENDPOINT=http://127.0.0.1:8080 \
DOGWOOD_CONTROL_ENDPOINT=http://127.0.0.1:8081 \
DOGWOOD_CONTROL_TOKEN=$(sed -n 's/^DOGWOOD_CONTROL_TOKEN=//p' .env) \
python3 -m unittest discover -s python-sdk/tests
# Ran 34 tests ... OK (skipped=1)

# ② 对同机直跑的引擎（不用 Docker；需要先 `cargo build -p dogwood-server`）
PYTHONPATH=python-sdk DOGWOOD_TEST_STORE_DIR=/tmp/dw \
python3 -m unittest discover -s python-sdk/tests
```

`DOGWOOD_TEST_STORE_DIR` 是**引擎的状态目录**，不是 socket 路径——SDK 会按
`<dir>/run/dogwood.sock` 推导。

## 2. 调试

### 2.1 看状态

```bash
# 容器活着吗
docker ps --format '{{.Names}}  {{.Status}}' | rg dogwood     # 看 (healthy)

# HTTP 面活着吗（会去 ping 引擎）
curl -s http://127.0.0.1:8080/healthz

# 引擎里装了什么
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8081/v1/status
```

`status` 里几个字段值得记：

| 字段 | 读法 |
|---|---|
| `rule_count` | 0 = 没装策略，此时一切请求都会被拒（fail closed） |
| `decision_kinds` | 哪些 kind 是决策点。**读它，别硬编码 `request`** |
| `partition_key` | 空 = 不可分片；非空 = 历史按这些字段分键（demo 是 `callerPrincipal`） |
| `log_offset` | 累积事件数。重启后不归零，可用来确认持久化生效 |

### 2.2 看协议：逐帧打印

```bash
DOGWOOD_TRACE=1 PYTHONPATH=python-sdk python3 -c \
  "from dogwood_sdk import DogwoodClient; print(DogwoodClient().ping())"
```

SDK 这一侧会打出它发/收的每一帧。HTTP 那一侧想看得更细就用 `curl -i`。

### 2.3 看日志

```bash
docker logs -f dogwood
docker logs dogwood 2>&1 | rg 'starting|engine exited|disk-space'   # 启动与退出原因
```

### 2.4 症状 → 原因

| 症状 | 原因 |
|---|---|
| `ps` 里没有容器 | 没起来：`docker run … dogwood-allinone` |
| `Up` 但一直 `(unhealthy)` | 探针打不到引擎，看 `docker logs dogwood` |
| `Restarting (1)` | 反复退出，看日志最后一句 |
| 请求全 **403** | **策略拒绝**，不是故障：`rule_count` 是 0？动作名带引号了？ |
| **401** | 没带 token / 带错 / 粘的时候多打了 `Bearer ` 前缀——这是**正常工作** |
| **502** | 引擎没起或已退出；看日志 |
| **504** | 引擎卡住；**504 是歧义的，不要盲目重试 submit** |
| `Database already open. Cannot acquire lock.` | 同一个 store 卷被另一个容器打开着（见 §3.2） |
| 改了 `.env` 里 token 但一直 401 | `restart` 不重读环境变量；用 `up -d` 或重建容器 |
| `docker build` 卡在拉镜像 | Docker Hub 不可达；本项目基础镜像可预先 `docker pull` |

## 3. 几个踩过的坑

### 3.1 deny 是 403，不是 `200 + allowed:false`

刻意反直觉：这样「看 2xx 就放行」和「没抛异常就放行」两种天真写法都自动 fail-closed。
代价是 deny 会进 4xx 指标，看板要排除。引擎自己的 CLI 也是同一个选择（deny 时退出码非零）。

### 3.2 一个 store 卷同时只能被一个容器打开

```
dogwood-server: open store: durable log: open durable log:
  Database already open. Cannot acquire lock.
```

redb 对 store 文件持**排他锁**。两个进程同时写一个日志会毁掉它，所以后起的那个直接退出。
这不是 bug。要并行跑多个引擎，用**不同的卷**。

### 3.3 如果你将来要把两个面拆成多容器：两个坑在等着

现在的单容器部署不受这两条影响（同容器、同 uid，天然满足）。但一旦按 uid 拆开：

**① `0700` 的状态目录让数据 socket 对别的 uid 不可达。** 引擎把状态目录设成 `0700`
（里面是策略集和日志，这是对的），而路径解析要求沿途**每个**目录都有 search 权限，
所以位于其下的数据 socket 对任何其他 uid 都不可达——**socket 自己是 `0666` 也没用**：

```
uid 10002 → connect /var/lib/dogwood/run/dogwood.sock
          → Permission denied (os error 13)     # 因为 /var/lib/dogwood 是 0700
```

这和引擎注释里"`run/` 是 `0711`，所以 agent 能连"的说法矛盾：`0711` 是给 `run/` 自己设的，
上面的 `0700` 轮不到它生效。绕法是把 socket 目录单独成一个卷，挂在一条可穿越的路径上。

**② `SO_PEERCRED` 跨 PID namespace 会失败。** 控制面用内核 peer credential 认证调用者，
而它报的是对端的 **pid**；跨 PID namespace 时那个 pid 不可映射，于是：

```
peer attestation failed: SO_PEERCRED: Unknown error -10001 (os error -10001)
```

同容器内连接正常。绕法是让控制面客户端和引擎同 PID namespace（Compose 里 `pid: "service:engine"`）。
另外：控制 socket 是 `0700`，所以控制面客户端**还必须和引擎同 uid**——引擎的
`--control-uid` 旗标看着能放宽，但 0700 的 socket 让别的 uid 在 `connect()` 就被拒。

### 3.4 引擎没有 TCP 监听

`dogwood-server` 里只有 `UnixListener`。所以"让引擎自己监听 TCP"不是打开一个开关——
要给上游加 TCP listener，而那会删掉 uid 认证（控制面靠 `SO_PEERCRED` 才知道"你是谁"）。
网络面就是适配器，它在容器内部替你走 socket。

## 4. 状态管理

```bash
# 看
docker ps -a --format '{{.Names}}\t{{.Status}}'
docker volume ls | rg dogwood

# 停 / 起（保留容器与数据）
docker stop dogwood && docker start dogwood

# 删容器、留数据（重建后策略与历史都还在）
docker rm -f dogwood

# 连数据一起清
docker volume rm dogwood-state
```

**持久化在卷里，不在容器里。** 删掉容器再用同样的 `docker run` 起来，`/v1/status` 里的
`rule_count` 和 `log_offset` 会原样回来——这是引擎的持久化能力，值得亲眼看一次。

改了 Rust 代码要先重建镜像（`docker build -f Dockerfile.allinone …`），
`docker restart` **不会**重读代码，也不会重读 `.env`。
